01

Pull, Congressional Bill Tracker

The project is about tracking every bill in the 119th U.S. Congress and helping people act on them.

My role
I own the database schema and the data pipeline. We are a team of 4.
Stack
Python, FastAPI, PostgreSQL, Alembic, pytest, GitHub Actions
github.com/NYU-Congressmen/congress-tracker

19,841 / 19,841

bills in our database, the same as Congress.gov. Before I fixed it, every sync was losing 90 bills without any error.

  • 26requests to load all summaries, instead of about 19,700
  • 0.08 sto show a cached bill text diff (0.60 s the first time)
  • 14PostgreSQL tables I designed
  • 83tests passing in CI

Problem

Congress.gov has the data, but it does not give bill status, it has no search across bills, and everyone shares a limit of 5,000 requests an hour.

If our app called it live, we would run out of requests, and we still could not answer simple questions like which AI bills passed the House.

Research

Before writing any code, I went through the API to understand its limits and traps.

  • It gives at most 250 items per page, uses offset paging, and has no status field at all
  • "Rule H. Res. 436 passed House." looks like the bill passed, but it is only a procedural vote. So I only trust the official wording when I set the status

Approach

What we do is copy the data into our own PostgreSQL database on a schedule and serve everything from there.

  1. Congress.gov API5,000 requests/hour
  2. Synccount-checked, idempotent upserts
  3. PostgreSQLconstraints in the database
  4. FastAPIsearch, filters, diffs
  5. React appnever calls Congress.gov

The status of each bill comes from its action history, and it never goes backwards. I also put rules like "one review per user per bill" into the database as UNIQUE and CHECK constraints, so a bug in the frontend cannot save bad data.

What went wrong

Every sync said 19,832 bills were saved, but the database had fewer.

There were no errors and the totals looked fine. My first two ideas (sorting again and reading again) did not hold up when I checked the data. The real cause was that the list was sorted by a date field, and 2,023 bills had the same date, so the pages split them differently each time. Sorting newest first lost 90 bills on every run, and oldest first lost 49.

Result

I switched to a stable order and added a check against the count the API reports. If something is missing, it reads again and removes duplicates.

I wrote a test that fakes the API and drops one bill on purpose, to make sure the second pass gets it back. Now production has exactly the same bills, summaries and 539 current members as Congress.gov.

02

AskNYC Zoning Assistant

You ask a question about NYC zoning in plain English, and you get an answer from the Zoning Resolution with the sections cited.

My role
I built it alone, from start to finish
Stack
Python, FAISS, Sentence-Transformers, Llama 3.1 (Ollama), Streamlit, Docker
github.com/ekberby/AskNYC

Every answer has a source

The model can only answer from the zoning text it found, and it has to name the section for each claim.

  • Top 3section-tagged passages for each question
  • 3,000characters at most in each passage
  • 1command to run it, fully local

Problem

Zoning rules are hard to read, and a chatbot that makes things up would be useless here.

For rules like these, an answer is only useful if you can check where it came from.

Approach

First it finds the right passages, then the model answers only from them.

  1. Questionplain English
  2. Embedall-MiniLM-L6-v2
  3. FAISS searchtop 3 passages
  4. Llama 3.1answer only from passages
  5. JSONanswer + sources

Key decisions

I wanted every passage to point back to a section, and I wanted everything to run on my own machine.

  • Each passage keeps its section number, title and link. Passages overlap a little so the context does not get cut at a boundary
  • I normalized the vectors and used an inner-product index, so the search works as cosine similarity
  • The model runs locally with Ollama, so there are no API costs or keys. Everything is packaged in Docker

Current status

It works from start to finish, but I have not measured its accuracy yet.

My next step is to make a small set of zoning questions with known answers and check how often it cites the right section.

03

Satellite Land-Use Classification

The project is about sorting Sentinel-2 satellite images into 10 land-use types, which is useful for urban planning and environmental monitoring.

My role
I did it alone
Stack
Python, PyTorch, ResNet18, Google Colab
github.com/ekberby/Deep-Learning-Land-Use

92.6%

test accuracy on the EuroSAT dataset, which has 27,000 images in 10 classes.

My model92.6%
Random guessing10%

Approach

Instead of training from zero, I used a model that already knows images and trained only the last layer.

I took a ResNet18 pretrained on ImageNet, froze it and added a new 10-class layer. It reached about 90% accuracy after just one epoch.

What went wrong

It mixes up crops with other vegetation, and highways with rivers.

From satellite height these look very similar in texture and color, so the problem is in the images themselves. Classes that look different do much better: forest and sea/lake get 97–99% precision.

04

NYC Bus Speed Prediction

We predicted bus speeds and severe delays, and ranked which routes should get bus-lane cameras next.

My role
We were a team of 4. I worked on data integration, the regression and classification models, clustering and the route ranking
Stack
Python, pandas, scikit-learn
Code
It was a course project, so there is no public repository

R² 0.704

for predicting bus speed with a random forest. For severe delays we got a ROC-AUC of 0.900.

Random forest0.704
Linear baseline0.435

Problem

NYC buses are slow, and only some routes have bus-lane cameras. We wanted to know which routes should be next.

Research

We merged 5 transit datasets into one table with 6.14M rows.

It had segment speeds, wait times, 4.76M camera violations, the list of enforced routes and hourly ridership, with no missing values.

What went wrong

We found three traps that would have made our results look better than they really were.

  • Random split: bus speed changes by season, so a random split lets the model see the future. We split by time instead
  • Linear models: they got stuck at R² 0.435 because time of day and distance do not affect speed in a straight line. Random forests fixed that
  • Simple comparison: routes with cameras look slower (8.07 vs 9.33 mph) only because the cameras were put on slow routes first. So we compared each route with itself, before and after

Result

In the end we had a ranked shortlist of routes for the next cameras.

  • +6.42%average speed increase on routes after cameras
  • 7routes stayed in the top 10 under every weighting
  • 0.0007standard deviation of R² over 10 random seeds

The busiest routes already have about 95% coverage. The routes that still need cameras are mostly in Queens and Brooklyn.
